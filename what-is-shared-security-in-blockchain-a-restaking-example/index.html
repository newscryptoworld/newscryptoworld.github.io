What Is Shared Security in Blockchain? A Restaking Example

What is shared security in blockchain? It lets an additional service use stakers’ and operators’ economic backing, while restaking brings rewards and slashing risk.

Crypto Record EditorialNov 18, 2026 · 08:29 UTC3 min read

Shared security in blockchain lets an additional service rely on economic backing from stakers and operators who also secure another network. The service can draw on existing staked capital and operator participation instead of building its entire security base from scratch.

One way to see the model is through eigen layer, an Ethereum restaking protocol. Restaking connects stakers, operators and additional services, called AVSs. For background on whether EigenLayer is a Layer 2 or restaking protocol, see our related explainer; it clarifies where eigen layer fits before we trace how its security model works.

How does shared security work?

Shared security works by assigning existing stake to support an additional service under that service’s rules. The basic sequence has four moving parts:

  1. Stake is restaked. A participant uses staked ETH or liquid staking tokens to take part in securing an additional service.
  2. Stake is delegated. The restaker delegates the stake to an operator. Delegation gives that operator responsibility for performing agreed duties; it does not make the operator the owner of the stake.
  3. The operator serves an AVS. The operator performs the service’s duties under the AVS’s rules. An AVS is an additional service that uses EigenLayer restaked assets and operators for economic security.
  4. The stake backs the service. The AVS can rely on the assigned stake as economic backing. Its rules may specify faults that expose allocated stake to slashing.

Think of the stake as a bond attached to a job: it gives the service economic backing, while the operator does the work. The analogy stops there; the actual duties and slashing conditions come from the AVS’s rules.

Take an illustrative service that needs operators to check whether submitted data meets its rules. A restaker delegates stake to an operator who takes on that AVS’s duties. The AVS can then use the assigned stake as economic backing. If the operator meets the rules, the restaker may receive rewards; if a specified fault occurs, the allocated stake may face slashing.

This arrangement can give an AVS access to staked capital and operator participation that already exist. The service does not have to depend only on a security base it builds itself. In exchange, restakers accept that their stake may be exposed to the AVS’s specified slashing conditions. Restaking can therefore create additional reward opportunities alongside additional risk.

The boundary matters: shared security means shared economic backing. An AVS remains a separate service; using restaked assets does not make it part of Ethereum consensus or give it Ethereum’s consensus rules. It has its own duties and rules, even when restakers use Ethereum-linked assets to support it.

What is the difference between shared security and a separate validator set?

With a separate validator set, a service relies on its own group of validators and the stake assembled for them. With shared security, an AVS can use existing restaked assets and operators for economic backing rather than relying only on a security base it builds independently.

That distinction describes the source of the economic backing, not a transfer of consensus. An AVS using restaking does not become Ethereum or automatically inherit Ethereum’s way of reaching consensus. The AVS’s own rules define what operators must do and which specified faults can put allocated stake at risk.
