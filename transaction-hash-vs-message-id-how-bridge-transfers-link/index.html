Transaction hash vs message ID: how bridge transfers link

Transaction hash vs message ID in bridge transfers: the hash identifies a transaction on one chain; the message ID links it to the destination transaction.

Crypto Record EditorialNov 28, 2026 · 05:14 UTC3 min read

A transaction hash identifies one transaction on one blockchain; a message ID identifies the cross-chain message connecting the source transaction to its destination transaction. A bridge transfer spans two chains, so it has a source hash and a destination hash, while the message ties those transactions to the same transfer.

Think of the hashes as the receipts from two separate stops, and the message ID as the reference connecting them. The source transaction records the burn or lock of tokens; the destination transaction records their mint or release. For a USDC cross-chain transfer, that distinction helps explain why a USDC bridge can show more than one transaction hash for a single transfer.

What each identifier points to

A transaction hash points to one transaction on one chain. It lets an explorer locate that transaction and its details, such as the contract activity recorded there. It does not, by itself, name the related transaction on another chain.

A message ID points to the cross-chain instruction or message that the bridge carries between chains. The bridge uses that message to connect the source-side action with the destination-side action. The exact identifier depends on the bridge protocol, so “message ID” is a general idea rather than one universal format.

The distinction matters when one source transaction emits several messages. The hash identifies the whole transaction, which may include multiple bridge-related actions. A message ID, or a protocol’s sequence number, singles out one of those messages. That makes it a more precise reference for one transfer when the source hash alone could match several.

Bridge explorers often let you enter the source hash and resolve it to a message, then show the corresponding destination transaction. In that view, the hash is the starting point on the source chain; the message is the link across chains; and the destination hash is the record of what happened on arrival.

How it looks in CCTP and Wormhole

In Circle CCTP, a USDC bridge transfer from Ethereum to Solana starts with a source transaction on Ethereum. That transaction burns USDC and emits a MessageSent event containing the message. Circle’s attestation service signs the message, and the destination-side process uses it to mint USDC on Solana. The Solana transaction has its own signature.

So the Ethereum hash identifies the source transaction, the attested message connects the source action to the destination action, and the Solana signature identifies the mint transaction. They refer to different parts of one transfer. Circle’s CCTP documentation describes the MessageSent event and attestation flow; the message is what lets the destination process act on the source event.

Wormhole uses a different identifier structure. A VAA—a signed message—can be identified by its emitter chain, emitter address, and sequence number. Wormholescan uses those details to distinguish a particular message. The sequence number helps pick out one message even when multiple messages originate from the same emitter; the source transaction hash still identifies the transaction that recorded the emission.

That difference is why a Wormhole VAA is not simply another name for a transaction hash. The hash locates an on-chain transaction. The VAA’s identifying fields locate a cross-chain message. Wormhole documentation describes VAAs through their emitter chain, emitter address, and sequence number.

When tracking a transfer, use the source hash to find the source-chain transaction, then use the message ID or protocol-specific sequence to identify the exact cross-chain message. The destination hash or signature identifies the transaction that completed the transfer on the other chain.
